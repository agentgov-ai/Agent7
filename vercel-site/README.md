# AgentGov — public product site (`vercel-site/`)

A **standalone, frontend-only** copy of the AgentGov product website plus an interactive
demo dashboard, ready to deploy to Vercel as the public marketing site.

There is no backend here. No FastAPI, no database, no API calls, no `localhost`.
Everything renders from a static fixture in the browser.

---

## Run locally

```bash
cd vercel-site
python -m http.server 3000
```

Then open:

| URL | Page |
|---|---|
| http://127.0.0.1:3000 | Product landing page |
| http://127.0.0.1:3000/dashboard.html | Interactive demo dashboard |

The pages also work if you just double-click `index.html` — all paths are relative and
the demo data is a plain `<script>` include, so nothing is blocked by `file://` CORS.
(`/dashboard` without the `.html` is a Vercel rewrite and only works once deployed.)

---

## Deploy to Vercel

1. Push this repository to your Git host.
2. In Vercel, **New Project** → import the repo.
3. Set **Root Directory** to `vercel-site`.
4. Framework Preset: **Other**. Leave Build Command and Output Directory empty —
   this is a plain static site with no build step and no `package.json`.
5. Deploy.

`vercel.json` handles routing:

| Route | Serves |
|---|---|
| `/` | `index.html` (Vercel static default) |
| `/dashboard` | `dashboard.html` (rewrite) |
| `/dashboard.html` | `dashboard.html` (direct) |
| `/assets/*` | static assets, cached 1 hour |

## Static demo vs. the real dashboard

| | This site (`vercel-site/`) | Real operational console |
|---|---|---|
| Hosting | Vercel, static | FastAPI service at `/ui/` |
| Data source | `assets/demo-data.js` | Evidence API + SQLite evidence store |
| Capability discovery | Fixed fixture | Real output of the codebase scanner |
| Review decisions | In-memory, reset on refresh | Persisted, survive rescans |
| ACAP generation | Appends a version in page memory | Real versioned ACAP records |
| `governance.yaml` | Built in the browser from fixture state | Generated by the API from the active ACAP version |
| Run ACAP Rules | Re-implements 2 rules in JS over fixture events | Full rule engine over the real evidence store |
| Findings | Recomputed locally | Stored, deduplicated, linked to real event IDs |
| Assessment | Frozen fixture snapshot | Recomputed on demand |
| Discovery upload | Not available | `POST /discovery/upload` |
| Demo reset / Export report | Not available | Available |

### The real operational dashboard still lives in FastAPI

> **Warning.** This is a stakeholder demo, not the product.
> The operational dashboard — the one that reads real runtime evidence, persists review
> decisions and generates real ACAP versions — still runs inside the AgentGov service at
> `/ui/`, alongside the Evidence API, SDK, scanner, ACAP generation and runtime rules.
> Nothing in this folder replaces it, and nothing in this folder talks to it.

## What the demo dashboard actually does

All of it is real UI over local state. Nothing is faked with a screenshot, and nothing
calls a server.

- **System selector** — switches between `gaming-agent-demo` and `support-api`.
  Re-selecting a system resets its state, which is the easiest way to restart the demo.
- **Six tabs** — Overview, Capability Discovery, ACAP, Runtime Evidence, Findings, Assessment.
- **Capability review** — Approve / Edit / Reject / Not a Capability mutate review state,
  update badges, and flip the *Human Reviewed* step of the Governance Loop.
- **Generate ACAP Version** — recomputes allowed vs. denied from review state and appends
  a new version to the history.
- **Preview / Download governance.yaml** — built in-browser from the approved capabilities,
  in the same shape the API emits. Denied capabilities never appear in it.
- **Run ACAP Rules** — replays the fixture's runtime events against the active ACAP version
  and produces findings, which then appear in the Findings tab.
- **Audit status** — visibly changes as you move through the loop.

The two rules reimplemented in `dashboard.js` are the ones that matter for the story:

| Rule | What it catches |
|---|---|
| `R_ACAP_denied_observed` | A tool a human explicitly denied was invoked anyway |
| `R_ACAP_approval_required_missing` | An approval-required tool ran with no *trusted* approval evidence |

The second one is the subtle one. `approval.granted` is self-reported by the agent and is
**not** trusted evidence — only an explicit `approval.verified` (or `trusted` /
`token_verified`) flag from the approving system counts. The demo's
`purchase_in_game_skin` event claims `granted: true` with no verification, and is caught
for exactly that reason.

## Demo data

Single source of truth: **`assets/demo-data.js`** (`window.AGENTGOV_DEMO`). Edit that file
to change the demo; there is no build step.

Its shapes mirror the real Evidence API responses (discovery, ACAP versions, coverage,
events, findings, risk profile, framework applicability, assessment), including the
honest bits: the coverage matrix keeps its `missing` and `annotation_required` rows, and
evidence confidence stays `low` because a required field is missing. Missing fields are
reported as missing, never fabricated.

**Privacy.** Synthetic data only. No real prompts, responses, API keys, tokens, emails,
customer data, or secrets. Identifiers such as `sha256:…` session and actor values are
illustrative strings, not hashes of anything real. Nothing was copied from `.env`,
`evidence.db`, or `artifacts/governance/`.

### Two honest caveats about the fixture

1. **State resets on refresh.** Every action is in-memory. This is a demo, not storage.
2. **Findings carry frontend fixture enrichment.** The demo findings include
   `failed_control`, `failed_control_title` and `framework_mappings` so the Findings
   detail panel can show its Failed Control and Framework Mappings sections. The live
   backend's ACAP rules do **not** emit those fields yet — `run_all_acap_rules` skips
   `control_library.enrich_finding`. That is a real gap in the backend, recorded rather
   than hidden.

## Product story

The site keeps the four-clause principle end to end:

> **Scanner suggests. Human approves. Runtime proves. Rescan shows drift.**

Observed behavior is never treated as authorization. The scanner proposes a catalog; a
person approves the operating boundary; runtime evidence shows what actually happened.
